# **Project Papercut — Claude Bible**

**Companion to the design doc. Not a replacement for it.** The design doc defines *what the game is*. This doc defines *how it is modeled in code*, and — more importantly — marks everything that is **not yet decided**.

---

## **0\. How to use this document**

* The design doc is the authority on intent. This doc is the authority on structure and vocabulary.  
* Items marked **\[DECIDE\]** are open. **Do not resolve them by picking a reasonable default.** Ask, or implement the narrowest version that leaves both options open, and say which you did.  
* Items marked **\[TENTATIVE\]** are features that may be cut. Do not build them unless asked.  
* Items marked **\[LOCKED\]** are settled; changing them requires an explicit instruction.  
* When something isn't covered here at all, that's a gap, not permission. Flag it.

### **Standard of work**

**Scope is provisional. Quality is not.**

This project has phases, but it does not have a throwaway phase. Everything built — including work done during Checkpoint 1 to answer open questions — is shipping code until proven otherwise, and should be written to be lived with. Do not write deliberately disposable implementations, do not leave known-broken paths, and do not defer correctness on the grounds that it's "just the prototype." In practice, the prototype *becomes* the game; treat it that way from the first commit.

The uncertainty in this document is about **which features exist**, not about how well they should be built. Handle that uncertainty structurally, not sloppily:

* Systems get clear boundaries and stable interfaces, so that cutting a feature means deleting a component, not unpicking it from three other systems.  
* Features are data and components, not branches inside core systems.  
* If something might be replaced later (see §4 rendering), put it behind an interface so the swap is contained — then build the current version properly.

**Robustness is not speculative generality.** Do not build abstraction layers, plugin systems, or configuration surfaces for features that don't exist yet. Robust here means: correct, readable, tested where it matters, no silent failure, no hidden coupling. It does not mean pre-generalized. When a choice is between the simple correct implementation and a flexible one, take the simple correct one — flexibility comes from clean seams, not from extra layers.

Timeline context, for prioritisation only and never as a licence to cut corners: 3–4 months total, mechanics prototype at \~5 weeks. If quality and deadline genuinely conflict, reduce scope and say so rather than lowering the standard.

## **2\. Glossary (use these terms consistently in code and comments)**

| Term | Meaning |
| ----- | ----- |
| **Sheet** | One physical piece of paper. The persistent world object. |
| **Screen** | The sheet the player currently occupies. One sheet \= one screen. |
| **Front / Back** | The two faces of a sheet. |
| **Flap** | The portion of a sheet that has been folded over. |
| **Crease** | The line a fold pivots on. Persists visually after unfolding. |
| **Base** | The un-folded remainder of the sheet — the part that doesn't move. |
| **Desk** | The world space containing the grid of sheets. |
| **Flip** | Viewing a sheet's back *without* folding (see §6) — distinct from folding. **\[TENTATIVE\]** |
| **Seam** | Where the landed Flap's edge meets the Front — the mirror image of the anchoring sheet edge(s). The crease is the Flap's other boundary. Where tape would go. |

Avoid "page," "paper," "flipside," and "tile" in code. They're fine in the design doc; here they cause drift.

## **3\. Spatial model**

**Not tile-based. \[LOCKED\]** Objects are placed at free positions and move continuously. Do not build a grid, tilemap, or cell-based pathing system.

* Sheet dimensions: 8.5 × 11, landscape (11 wide × 8.5 tall).  
* **\[DECIDE\]** World unit scale — is 1 unit \= 1 inch of paper, or is the sheet normalized (e.g. 11 × 8.5 units)? Pick one early and never mix.  
* Terrain (traversable / untraversable) — **\[DECIDED — provisional, 2026-08-25\]**: placed objects with box colliders, over art drawn outside Unity. Aaron: *"drawing the maps in photoshop, then doing the collision/terrain in Unity for the fine tuning ... I don't know that I need the collision to be more than boxes."* Ground is the sheet surface itself (no component). A region is a `TerrainRegion` with a `BoxCollider2D`; it is a wall, or it is crossable only with a player `Ability` (water needs Swim) — kinds are prefabs differing in data, not code. **Cost of this choice, deliberately deferred to the occlusion task:** a box partially under a flap must either be clipped at runtime (box → polygon) or handled by a per-region coverage rule; that is the "how folding clips terrain" fork and it feeds §5. There are no authored exit boxes any more (see §7); a region at a sheet edge simply means there is no room to arrive there. **Revised 2026-09-10** (Aaron, offered convex-only / any-polygon / art-derived collision: *"Yeah, can you implement 3?"* — any polygon; and *"Both shapes, separate prefabs"*): a region's authored collider is a `BoxCollider2D` **or** a `PolygonCollider2D` holding **one simple outline** of any shape — concave allowed, no holes (Aaron: single outline only; an island is a separate region). A polygon is split into convex pieces at load (`PolygonDecomposition`: ear clipping + convex merge) and every consumer of a footprint sees pieces (`FaceFootprint`), so folding clips a polygon exactly as it clips a box. `Wall (Polygon)` / `Water (Polygon)` prefabs sit beside the box ones; existing box regions are untouched. The Sheet Studio draws a polygon point by point and edits vertices (drag; drag an edge midpoint to insert; right-click a vertex to remove); an edit that leaves the outline self-crossing reverts on release (Aaron), and vertices magnet to other regions' vertices and the sheet edge (Aaron).  
* **Props \[DECIDED — 2026-09-10\]:** static scenery (the Tree) is art only — no collider of its own. Aaron: *"I would rather separate out the collision from those objects, and manually put it over them. I think for objects like trees its just kinda clunky with them individually having collision."* Its collision is authored by laying Wall regions over the drawing in the Studio. A prop lives in `Prefabs/Props`; the Studio picks, outlines and fold-previews it by its sprite's rect (`StudioPlacement.IsProp`).  
* **Collision view \[2026-09-14\]:** static terrain is invisible as shipped (the map art is the drawing), which is no good for testing a sheet before its art exists. Aaron: *"give an option per page in the editor to make the collision visible or not … in solid colors, so its very clear."* Each sheet has `Sheet.showCollision` (the Studio toolbar's **Collision** toggle, saved with the variant); while it is on, `TerrainFill` on the Wall/Water prefabs draws the region's collider as a solid fill (colour per prefab) as face content on the region's own layer, so it folds, clips and mirrors like everything else and the fold and occlusion systems never know. Shown in the game and in the Studio panes alike. Cutting it is removing the component from the prefabs; the Gate keeps its own sprite.  
* **Universal and filter regions \[2026-09-28\]:** Aaron asked for *"a new kind of wall, one that conceptually exists above the surface of the paper, and so when the page is folded, the wall still persists. It should still render as if it were limited by the edge of the paper ... You can call it a universal wall"*, and *"another kind of wall that doesn't block the player, but does block Blocks, and its derivations like pushable paperweights"* - filter walls, *"universal or not"*. Two independent axes on `TerrainRegion`, both data: **who** it blocks (`TerrainBlocks` flags - Player, gated by `requiredAbility` as before, and/or Blocks; Wall and Water block both, a filter wall blocks Blocks only) and **where** it lives (`universal`: under the Sheet's third content root, **Above**, in sheet space; Aaron named it). A universal region is never lifted, mirrored, covered or carried: `SheetOcclusion` clips it to the union of the sheet's layers (`SheetLayers.CoverageAbove`), so it ends exactly at a folded-down edge and still blocks on a landed Flap; unlike face content it is trimmed to the sheet rect even when flat. It never holds a fold short (Aaron: the Flap goes under). Blocks skip a region that does not stop blocks in their push cast (`PushableBlock.TryPush`); the player's passability is the same ignore-pair as Water's, and a filter wall is passable even with no `PlayerAbilities` at all. **A fold whose Flap would carry a block under a block-stopping universal wall is refused, red, like the player rule** (Aaron: *"Deny the fold if a block falls under a universal wall, like with folding over the player"*): `FoldLandingRules` through the block's `IFoldConstraint.RefuseFold`, `FoldRejection.CarriesBlockUnderWall`, judged on the stack after the fold so a Back-side block the fold would expose under a wall is refused too; the Sheet Studio's preview refuses the same from the authored blocks and walls (an editor limit: blocks are judged where they are authored). Prefabs in `Prefabs/Terrain`: `Universal Wall`, `Filter Wall`, `Universal Filter Wall`, each with a (Polygon) twin; collision fills teal for universal (Aaron: *"Make it teal"*, over Water's blue), violet for filter (mine). A universal fill is main-camera content clipped through the sheet's *displayed* layers, so it follows the drag preview and the unfold swing and stays on a sheet that is not the Screen. Studio: Above content is placed and edited in the Front pane, drawn read-only and mirrored in the Back pane (Aaron: *"number 2"* of hide / read-only / editable), and drawn clipped in the fold preview; a Wall dragged under Above or a universal region under a face refuses itself at Play and is drawn red. Art for universal walls comes later (Aaron). Cutting: delete the six prefabs; the Above root, the two fields and the landing rule stay inert.  
* Movement is continuous, but **\[DECIDE\]** whether it's 8-directional, fully analog, or grid-snapped-feeling-but-free.

**Consequence worth knowing:** with free placement, "is this thing covered by the fold?" becomes a geometry test against a polygon rather than a cell lookup. Everything downstream (blocks, terrain, exits, the player) inherits that.

## **4\. Fold model**

### **Geometry \[LOCKED unless noted\]**

* A fold is defined by a **crease line** plus which side of it becomes the flap.  
* Two legal crease families:  
  * **Edge fold** — crease parallel to a sheet edge, at any distance in from it.  
  * **Corner fold** — crease at exactly 45° to the edges, starting from a corner.  
* **\[DECIDE\]** Is fold depth continuous, or snapped to increments? Continuous is truer to paper; snapping serves pillar 3 ("the challenge is the puzzle, not reading the world"). Untested. *Kept open in code:* the model is continuous and `FoldDragInput.depthSnap` (Inspector, 0 = continuous) snaps the drag — play both.  
* ~~Flaps may extend past the sheet's boundary. A corner flap can overhang the desk. That's legal and should render.~~ **Reversed by Aaron, 2026-08-26:** *"I don't actually want to allow extension past the edge on folds. With the shape of the paper and size of the screen, I think there's just not enough room to make that interesting. Also opens some weird edge cases that I don't want to answer."* The landed Flap must lie on the sheet: `FoldGeometry.MaxDepth` (edge folds: half the extent; corner folds: the sheet height); input clamps, `SheetFolds.TryCommit` rejects. The Design Doc's "Folds extending beyond the sides of the screen" under *Valid Folds* is superseded. The geometry code stays general.

### **Validity**

* **Invalid:** any fold whose flap would cover the player, wholly or partially. **\[LOCKED\]**  
  * Structural consequence: **the player is always on the base, never on the flap.** The player can never be transported or flipped by a fold. Do not build fold-carries-player.  
* **Valid:** folds that partially cover objects. A partially covered pushable can be pushed fully under, or pulled out and pushed back on top.  
* **Paperweights hold a fold short \[DECIDED — 2026-09-14\]:** Aaron, after trying to design a level: *"I need an object that is placed on a sheet somewhere that blocks a fold from folding past that point ... This prevents massive folds from happening, which can invalidate a lot of potential puzzles."* A Flap may neither lift nor land on a face-up paperweight — the player rule's shape (Aaron: *"other than that, its the player rule"*) — but the drag is **clamped, not refused**: *"it just stops getting pulled ... it just can't stretch beyond that point, and when the mouse drags past it, just doesn't follow. It still doesn't get placed until the player releases the mouse."* `SheetFolds.MaxDepth` is now min(overhang bound, `FoldObstacles.MaxDepth` — the first-contact depth against every `IFoldObstacle` under the sheet), and 0 when that is below `minDepth` (no sliver that drops on release); `Evaluate` refuses `CoversObstacle` as a safety net. A paperweight blocks only through its face-up parts (Aaron: *"If its not on the same side, it doesn't block it"*; a covered part is inert and rides the paper); unfolds were unaffected at first (*"for now, unfolds aren't affected"*) — **revised 2026-09-24**, see below. The Sheet Studio's fold preview clamps and refuses the same way from the sheet's authored paperweights, and its fold list refuses edits that would put a fold over one. See §9 for the element.  
* ~~**\[DECIDE\]** Multiple simultaneous folds per sheet — flagged in the design doc as needing playtest. **Build the data model to hold a list of folds, but implement and expose only one at a time until told otherwise.**~~ **\[DECIDED — provisional, playtest, 2026-08-26\]** Aaron: *"Can we try allowing multiple folds on one sheet?"* Exposed behind an Inspector toggle, `SheetFolds.allowMultipleFolds` (base Sheet prefab). The sheet is modelled as a stack of layers (`SheetLayers`): each fold lifts everything on the Flap side of its crease and lays it over, so rendering, collision and occlusion are N-fold from the start. Folds stay an ordered list.  
* ~~**\[DECIDE\]** Folding an already-folded sheet (fold-on-fold, flap folded again) — same as above, assume no.~~ **\[DECIDED — provisional, playtest, 2026-08-26\]** Aaron: *"I do in fact mean stacking is allowed - but also make it a toggle."* `SheetFolds.allowStacking`: on, a fold may land on another Flap and may cut through one (the Flap side of the crease is folded over however many layers deep — one toggle for both, Aaron: *"one toggle"*); off, every fold must be independent of every other (their lifted and landed regions never touch; a crossing drag tints red, `FoldRejection.OverlapsFold`). A fold with a later fold on or through it cannot be unfolded first (`CoveredByLaterFold`). Landing into a region an earlier fold emptied is legal; the landed edge over empty desk is a wall, not an exit. **Revised 2026-09-16** (Aaron): with stacking off, a drag that would cross another fold is **clamped like a paperweight, not tinted red**: *"I want it to act more like the paper weight, so that the flap stops in place when it bumps into another flap. This makes it so you don't have to be uber precise if you want to place the flap directly next to another (where the player can then directly travel from flap to flap, which is a thing I want to do with some puzzles)."* `SheetFolds.MaxDepth` also holds short of every committed fold's lifted and landed pieces (through the same `FoldObstacles.MaxDepth`), so the independence rule is unchanged — the sheet a fold lifted away counts as much as its Flap (Aaron: stop at holes too) — and `OverlapsFold` is now the safety net, like `CoversObstacle`. The Sheet Studio mirrors the sheet's `allowStacking` for this (`StudioFoldModel.AllowStacking`; Aaron: clamp in the Studio too), holding the drag, refusing and guarding its fold list the same way; `allowMultipleFolds` stays ignored there (the 2026-08-31 scope).

### **Rendering \[DECIDED — provisional, 2026-08-26\]**

**Render-texture compositing**, chosen by Aaron from the three candidates (mesh deformation, stencil/shader masking, render-texture compositing): *"I think we can go with render-texture compositing. Its okay if itch hates me, I'm fine to make it a downloadable if necessary."* Lives in `RenderTextureFoldRenderer` behind `IFoldRenderer` (the seam between *what a fold does* and *how it is drawn*): a camera per face renders that face's content (on the `SheetFront`/`SheetBack` layers, which the main camera does not draw) into a texture; the visible sheet is a Base mesh from the Front texture plus a landed-Flap mesh from the Back texture through the fold's reflection (creases are shaded on these pieces; see *Crease normal maps* below). No readbacks; the WebGL cost is one small camera pass per visible face. Creases are part of the paper, not overlays (Aaron, 2026-08-26: *"the crease lines should instead be a part of the paper"*), so they fold with the sheet; ~~they were drawn as line content under Front and, mirrored, under Back~~ — superseded 2026-10-07 by the crease normal maps below. Authored face content lives in local z (−0.1, 0]. **Crease normal maps \[2026-10-07\]:** Aaron replaced the placeholder black crease lines with two crease normal maps (*"one for the front side, one for the back"*); a crease is now shading, not drawn content — each `CreaseMark` is a segment in one face's authored space, and the shading shader (`Paper Face` at first, `Sheet Shading` since the same day's revision below) lays a map along it (the image is a whole sheet with one crease across it, at sheet scale, centred on the mark, mirror-repeated past its ends) and blends it with the grain, so it still folds, hides and comes around with the paper and is lit from the Desk like the grain. Which map: **by fold direction** (Aaron) — `creaseInsideMap` (the Frontside image) on the face that was up when the fold was made, `creaseOutsideMap` (Backside) on the other; the same as Front/Back for every ordinary fold. The image's top faces the side that lifted, with a per-map flip toggle (Aaron). The maps are used as authored, with no lean correction (Aaron will re-export them flat). Live and remembered creases differ only in strength; at most 64 per face (Aaron), dropping the oldest remembered past that. `CreaseShading` packs and is the tested reference for the shader's maths. Tunables on `RenderTextureFoldRenderer`: the two maps, their line heights and flips, `creaseMapWidth`, `creaseHalfWidth`, `creaseFadeStart`, `creaseStrength`, `rememberedCreaseStrength`. The Seam border is still a line (`seamMaterial`, `Seam.mat`). Not drawn in the Sheet Studio (as before). Elements sit at −0.05; the Block prefab's editor-only Drawing sprite (inherited by the paperweights) sits at −0.08 so that in the Sheet Studio a block or paperweight draws above walls and the other elements, as the main camera composites the runtime block mesh over the sheet in the game (Aaron, 2026-09-17: walls covered paperweights in the editor). Wrinkle art later is a shader on these textures (crease art now is; see *Crease normal maps* above). **Paper grain \[2026-09-21\]:** the paper's texture is that shader. Aaron replaced the placeholder paper image with a normal map (*"The map should go on top of everything on a sheet's side. There should be one for the frontside and the backside."*) and chose, offered the alternatives: a fake light in the shader over real URP 2D lights (none exist; cheap, WebGL-safe); the grain in the fold renderer's face material over an overlay quad per face (lit in Desk space, so a landed Flap is lit from the same side as the Base; not shown in the Sheet Studio panes); and a flat paper colour under it over keeping the image. So: the Surface quads' `Sheet` material is a flat colour and the face material is `Paper Face` (shader `Papercut/Paper Face`), which draws each piece from its face texture and shades it through that face's normal map (since 2026-10-07 the shading is the separate `Sheet Shading` pass, see below) — `RenderTextureFoldRenderer.frontGrain` / `backGrain` (Back-space, like all Back content; both the same map for now), `grainLight` (Desk-space direction), `grainStrength`, `grainAmbient` — carrying the normal into Desk space by the piece's pose. ~~Over everything on the face, but not over the player or blocks, which the main camera composites on top.~~ **Revised 2026-10-07 — shading over everything on the sheet:** Aaron: *"I don't think the creases, or the paper wrinkles for that matter, are rendering over the player or any other real time object like boxes. They live on the paper too."* The grain and crease shading moved out of `Paper Face` (now face texture × tint only) into a second pass, `Sheet Shading` (shader `Papercut/Sheet Shading`, `RenderTextureFoldRenderer.shadingMaterial`), multiplied over everything the main camera has drawn on the sheet — the faces, the player, blocks, paperweights, and universal walls too (Aaron, asked: *"Yes, shade them too"*). Each layer mesh has a shading child sharing its mesh (same coverage and face uvs, so the shading still rides the paper and is lit in Desk space); the children sort after every order-0 renderer, topmost layer first, and a stencil bit (128) lets only the topmost piece shade a pixel. The Seam border stays at order 0 under the player, and is shaded. ~~**Authoring rule:** anything the main camera draws that lies on the paper must stay at sorting order ≤ 0 on the Default sorting layer; order ≥ 1 draws over the shading.~~ **Sheet warp \[2026-10-08\]:** shading alone read as *"looking at them through a dirty window that looks remarably like a wrinkled sheet of paper"* (Aaron) — nothing's shape followed the wrinkles. Chosen by Aaron from screen-space warp / per-object warp / stronger colour: *"do A"*. `Sheet Shading` now **redraws** each pixel of the sheet (Blend One Zero) from the 2D renderer's **Camera Sorting Layer Texture** — a copy of the screen taken after the **Default** sorting layer (Renderer2D: on, bound Default, full resolution) — sampled a little way off — drawn in toward each crease by a smooth **pinch** and moved by the grain's **broad** wrinkles (a blurred mip less its average lean) — times the same light (a first version moved pixels by the maps' slopes and read as *"a smearing effect instead of the things just following the folds"*, Aaron; he chose the pinch + soft wrinkles): the faces' drawings, the player, blocks, paperweights, universal walls (Aaron: *"Warp like the rest"*, revisit when wall art exists) and the Seam bend with the creases and, more faintly, the grain (Aaron: *"Both, grain weaker"*). The shading parts sit on their own sorting layer **`Sheet Shading`** after Default; the offset of each part is held inside its outline — its layer's edges and those of every layer above (`SheetWarp`), less a screen pixel — so nothing is pulled across a Flap's edge, a Seam or the sheet edge; the pinch profile is `sign(a)·w·x·(1−x)²` across the band (one-to-one for strengths −0.9…2.5, so a drawing never folds over itself), crease pinches blend continuously (`Σ|v|²v/Σ|v|²`) and ease out at a crease's closed ends. Tunables (`RenderTextureFoldRenderer`, Warp): `creaseInsidePinch` / `creaseOutsidePinch` (default 1), `rememberedCreasePinch` (0.4), `grainWarp` (0.6), `grainWarpBlur` (mip 4). Face cameras and the Sheet Studio's pane cameras use the pipeline's second renderer, **`Renderer2D Faces`** (no screen copy; `FaceCameraRenderer`). **Costs, flagged for WebGL (§1):** one full-screen GPU copy per frame on the main camera (no readback); the shading shader holds about 210 uniform vectors (64 creases × 2 + a 64-edge outline), under WebGL2's guaranteed 224. Overflowing the outline turns the warp off for that part (dev warning). **Authoring rule:** anything the main camera draws that lies on the paper must be on the **Default** sorting layer (any order); `Sheet Shading` is reserved for the shading parts, and anything on a later layer draws over the sheet, unwarped and unshaded. Cutting the grain is clearing the two grain maps (or `grainStrength` 0); cutting all shading (grain and creases) is clearing `shadingMaterial` (an error is logged) or setting every strength to 0.

### **Input \[DECIDED — provisional, 2026-08-26; the first scheme to prototype\]**

Press near an edge or corner of the Screen and drag inward; the grabbed edge/corner follows the cursor (edge depth = half the drag distance; the corner lands under the cursor); the fold previews live; release commits; right-click/Escape cancels. An invalid fold (would cover the player) tints red and release does nothing (Aaron: *"A for sure."*). With multiple folds on, a press tries the Seam (unfold) first, then a crease (grab that fold line, fold further), then the sheet's own edges and corners (new fold); with them off, a folded sheet only answers the Seam click. Lives in `FoldDragInput` on the Desk; every distance is an Inspector value.

## **5\. Occlusion & collision**

* A flap **covers** part of the base. Covered front content is hidden and non-interactive. **\[DECIDED — 2026-08-26\]** Covered terrain is gone for collision (Aaron: *"Yes, duh."*); a partially covered box region is **clipped at runtime** to its visible part (Aaron: *"a for certain."*). Mechanism: `SheetOcclusion` notifies every `IFoldOccludee` with what is left of it and where; `TerrainRegion` swaps its authored collider (box or polygon, see §3) for a clipped `PolygonCollider2D`. The clip is exact: each visible part is the footprint intersected with a layer of the folded sheet, placed where that layer lies, minus the layers above (`SheetLayers.Coverage`). Front content on a piece folded twice is Front-up again wherever it landed.  
* The flap's own surface is walkable — it presents the **back** of the sheet (see §6).  
* **Movable objects \[DECIDED — provisional, 2026-08-27\]:** a `PushableBlock` is clipped by folding exactly like terrain (`SheetPlacement`); a block partly under a landed Flap belongs under it (Aaron: *"if its covered at all, it belongs to the side that is covered by the flap"*) and can be pushed fully under; a block wholly clear of a Flap that is pushed into its edge climbs on top (*"if its pulled out, then it becomes part of the top, and if you push it over, it now goes on the top"*). Blocks stop at walls, gated terrain, sheet edges and other blocks (*"stop"*) - since 2026-09-28 only at terrain that is solid to blocks (`TerrainBlocks`, §3): a filter wall stops blocks and not the player; they roll across creases (boundary walls on a crease carry `CreaseWall`). **Hold to push or pull \[DECIDED — 2026-09-24\]:** walking into a block no longer moves it. Aaron: *"instead of being automatic recquire pressing down and holding space ... I want to allow pulling as well, so while the player is holding space, they should be able to pull the block as well. Pushing and pulling means only two directions, perpendicular to the side of the block the player is on."* With the `Interact` key down (Space / gamepad South) while touching a face of a block they may push, the player **holds** it (`BlockPusher`; one word, since the Fold map's `Grab` is the mouse): they move only along that face's axis, pushing the block ahead of them or pulling it after them at the block's push speed, and input across the axis does nothing (Aaron, offered release-on-sideways: ignored, stay held — so `SheetEdge` judges travel by what the player actually moves by, `PlayerMover.EffectiveMoveInput`, not by the raw input). The player moves exactly as far as the block did (`PushRules.FollowInput`), so a block stopped by a wall stops them and a pull never opens a gap; a pull first checks how far the player can walk back, ignoring terrain they may pass. Touching only, no reach (Aaron); a resting contact that lapsed at a standstill is covered by a contact-offset probe. The hold lets go on release, when the block stops being pushable (covered, off the Screen) or when the two drift apart by `BlockPusher.holdBreakDistance`. Without the key a block is a wall with no slowdown. A block pushed into the sheet edge stops there and so does the player (no travel while held); pulling a block into an edge strip travels as walking would, and the block resets with the sheet. A pull is `PushableBlock.TryPush` with the cardinal reversed, so every fold rule above applies unchanged: the Design Doc's "pulled out then pushed back on top" is now playable. Drawing: while holding still, `Scuffy Hold` (placeholder: the first push frame, until Aaron draws one); while pressing along the axis — push or pull, whether or not the block can move (Aaron: *"push loop as a strain"*) — the push loop; the drawing faces the block throughout (Aaron, offered facing the movement: face the block). **Pressure is a fact about the sheet, not about visibility** (Aaron: *"the buttons and the stuff on them don't disappear, they are just innaccessable because they are covered … its still holding the button down under the page"*): a `PressurePlate` is pressed while a presser's centre is on it on the same face of the flat sheet (`PressureRules`). **A block's drawing is never mirrored \[2026-09-24\]:** Aaron, seeing a paperweight mirror as it climbed a Flap: *"It shouldn't do that since its still on the 'front' side"* — and, offered paperweights only or every movable object: every movable object. A block's picture is laid out upright in Desk space around its centre wherever its layer carries that centre (`PushableBlock.DrawingUv`), on a Flap or revealed on the Back alike; only the clip to its visible pieces follows the paper. The Sheet Studio's fold-preview pane still draws a block's editor sprite as face content through the fold renderer, so a block under a previewed Flap there mirrors where the game would not — flagged, not fixed.  
* **\[DECIDE\]** Layering rule: does the player walk *on* the flap, or is stepping onto the flap surface the same as any other traversal? Are there height/edge effects at the crease, or is the world perfectly flat for movement? *Narrowest-open in code:* the world is flat; stepping onto the landed flap is ordinary traversal; the crease is a wall on the lifted side only. (Overhangs were briefly walkable — Aaron, 2026-08-26: *"it should be walkable for now"* — and then removed altogether the same day; see §4. Only the Screen has live physics, which still holds.) With several folds a landed edge lying inside the sheet rect over empty desk is also a wall (`OutlineKind.Wall`).

## **6\. Backside model**

**The single most confusable part of the system. Get the convention written down before writing code.**

When a flap folds over, the surface now facing up is the **back of the flap region, reflected across the crease line**. It is not "the back of the sheet" in general, and it is not un-mirrored.

* **\[DECIDED — provisional, 2026-08-24\]** Authoring convention: back-side content is authored **in the sheet's own Back-space, flat**, as the sheet looks when physically turned over about its vertical edge — Back point (x, y) lies directly beneath Front point (−x, y). Any mirroring across a crease is done at runtime by the fold system. Chosen by Aaron so a future level editor can show both faces flat and preview a fold from the same authored data. Revisit when the level editor exists. Lives in code as `SheetGeometry.BackToFront`; each sheet's Back content is authored under its `Back` root (see `Sheet`). The Back root is never moved at runtime (since 2026-08-26, multiple folds: one root cannot be posed for two Flaps); exposed Back content is placed through its occludee's clipped collider.  
* **\[TENTATIVE\]** A separate **flip** mechanic — a button/spot that shows the whole sheet's back, and/or an unlockable that lets the player move to the back freely. These are *different mechanics from folding* and may or may not ship. Do not implement without an explicit go-ahead, and do not conflate them with fold-reveals-back.  
* Back-side exits lead to the **front** of the neighbouring sheet, never to another sheet's back. **\[LOCKED\]**

Both scenes share every prefab and tunable default, but Inspector values on the Desk objects (drag feel, slide, camera) are per scene from here on.

## **9\. Puzzle elements**

**The entire contents of this section are \[TENTATIVE\]. Nothing here is committed.** *Built on Aaron's request (2026-08-27), as isolated playtest elements: pushable blocks (`PushableBlock`; `BlockPusher` is the player's hold, §5), pressure plates — Hold, Latch and (since 2026-09-21) Toggle as data (`PressurePlate`, pressed by any `IPlatePresser`; the mode table is `PlateRules`), effects behind `PlateEffect` (Apply/Revert/Toggle; one so far, `SwitchPresenceEffect`), and a `Gate` wall prefab. A target shared by several effects (a Gate wired to a Hold plate and a Latch plate) is removed while **any** of them holds it (`ObjectPresence`, added to the target at runtime) - fixed 2026-09-16 after a released Hold plate brought back a Gate a Latch had removed for good. Whether they ship is still the Checkpoint 1 call; cutting them is deleting those components and prefabs.*

*Gates that start off, many gates per plate, Toggle plates (Aaron's request, 2026-09-21: "gates … that start off, and turn on on a button press … multiple gates tied to one button, and pressing the button swaps them"):* every target has a **resting state** (`ObjectPresence.startsAbsent` — Aaron: on the gate, not on the wiring): `Gate` rests present and is removed while switched; `Gate (Off)` (a variant of Gate in `Prefabs/Terrain`, `startsAbsent` on) rests absent and is present while switched; the rest state is applied in `Start`, after every `Awake` on the object, so a resting-absent region still receives fold coverage while away. A plate's `SwitchPresenceEffect` holds a **list** of targets, each switched from its own rest, so one plate removes Gate A and presents Gate B together. **Toggle** (`PlateMode.Toggle`, the `Toggle Plate` prefab): each press *toggles* its targets (`PlateEffect.Toggle`); the plate holds no state of its own — the toggled state lives on the target — and it is tinted only while pressed. Combination: a target is switched while any Hold/Latch effect holds it **or** it is toggled; every press on any wired Toggle switches it again (Aaron: "every press switches it", two hallway switches), a held target ignores toggles visibly until the hold lets go, a fired Latch masks toggles for good. **Seeding** (Aaron): the plate's first tick, its first after being enabled and its first after the sheet reset take what is on the plate as its condition, not a press — a block authored on a Toggle plate leaves the puzzle as authored, and a block reset onto one on leaving switches nothing. Overlap is an authoring rule only (Aaron): a target must never be switched into a place where the player or a block can stand; nothing checks. The Sheet Studio's Link mode wires a plate to several targets (click each; a wired one unwires; empty space or Esc releases the plate), and draws a resting-absent element dotted with "(off)" in the face panes — the fold-preview pane renders it as the game would once switched. Cutting: delete `Gate (Off)`, `Toggle Plate`, `PlateRules`/the Toggle value, `ObjectPresence.startsAbsent`; the effect and presence components stay with the plates. `Ability.Push` exists (Aaron, 2026-08-27: *"you can add the ability, ig, but I won't use it for now"*); **since 2026-09-17 every block requires it** (the Block prefab's `requiresAbility`, inherited by the Pushable Paperweight — Aaron: all blocks; per-block override stays) and the Power Croissant grants it.

*Unlockables (Aaron's request, 2026-09-17 — "power ups"; the Design Doc's word is unlockable):* one component, `Unlockable`, on a prefab per unlockable differing in data (`grants`) and drawing; the first is `Prefabs/Objects/Power Croissant` (grants Push; Aaron's three-frame drawing, `Power Croissant Idle`). Collected by **walking over it** (Aaron: walk over, no key): the player's place on the flat sheet (`SheetPlacement.TryGetSheetPoint` — the point under their centre on the topmost layer there, on its up face; the same place a plate judges them by) is on the pickup's face inside its trigger box. Collecting calls `PlayerAbilities.Grant` (the one mutator; nothing revokes) and deactivates the pickup for the session (§8). It is face content like a plate: an `IFoldOccludee` whose box is clipped by folds, so one authored on the Back is collected by standing on the landed Flap that shows it and one under a Flap is unreachable. No pickup feedback beyond the croissant vanishing (UI/audio are outside prototype scope). The Test Desk's Player instance starts with Push so its block sheets keep working (Aaron, 2026-09-17); the Desk's Player starts with None. Cutting it is deleting `Unlockable.cs`, the prefab and the animation asset, and turning the Block prefab's `requiresAbility` back off.

*Paperweights (Aaron's request and name, 2026-09-14 — see §4 Validity for the fold rule):* two prefabs in `Prefabs/Objects`, both **variants of Block** carrying the `Paperweight` component (an `IFoldObstacle` over the block's visible pieces). `Paperweight` is fixed where it is authored (`PushableBlock.pushable` off — the block is a wall to the player and to other blocks and never moves; Aaron: *"a static thing that can be placed anywhere, including on top of walls and stuff"*, and *"the player can collide with both versions"*); `Pushable Paperweight` pushes, climbs, resets and rides like a block (*"acts like the pushable block that we have, except that it also blocks folds ... so I can use this mechanic to design puzzles revolving around it"*). Both press plates (Aaron, 2026-09-14: both). Fixed block-size footprint for now (Aaron: fixed; resizing may come later). A weight pushed wholly under a Flap is inert while covered (Aaron). A weight on a Flap holds that fold's unfold until it is pushed off (2026-09-24; see §4 Unfolding). Placeholder art: a push-pin clip-art drawing, one static frame (`Paperweight Idle`), untinted, fitted to the block's rect through the texture's import settings (2400 px per unit, pivot on the pin's centre; 2026-09-17, before that the Box drawing tinted) until Aaron draws paperweights. **Drawing clipped to its frame \[2026-09-24\]:** the pin touches its image's top and right edges, and the 2026-09-17 fit padded the PNG with a transparent margin so the block's mesh, which samples the texture across the whole block rect, never repeated a clamped opaque edge as a bar. Aaron replaced that copy with the unpadded original (*"do things the right way instead of adjusting the size"*), so `PushableBlock` now clips each drawn piece to the frame's flat-space extent (`PushableBlock.DrawingRect`, the rect `DrawingUv` lays the frame over): a block's drawing never draws past its image, and a frame smaller than the rect leaves the rest of the rect bare. Authoring rule unchanged: size the drawing to the rect with pixels-per-unit and the pivot, never by scaling the Drawing child (the block refuses a scaled or offset Drawing and goes invisible with an error). Cutting them is deleting `Paperweight.cs`, `PaperweightRules.cs` and the two prefabs; `IFoldObstacle`/`FoldObstacles` may stay inert like `IFoldConstraint` would without blocks.

These are a brainstorm list, not a feature list. Which of them ship gets decided at Checkpoint 1, after prototyping. **Do not implement any of them as a shipping feature without being told to.** If one is needed to exercise another system, build it to the same standard as everything else but keep it isolated, and say why it exists. Cutting it later should mean deleting a component and its prefab — never unpicking it from the fold or occlusion systems.

Element ideas currently floated:

* Traversable / untraversable terrain  
* Pushable blocks and other pushable elements  
* Buttons (pressure)  
* Switches, instant effect (e.g. opens a door)  
* Switches, on/off toggle  
* Toggle-visible blocks (Mario on/off blocks)  
* A flip button/spot that shows the sheet's back  
* Front-only / back-only blocks  
* Elements that float up on top of the flap when covered by a fold  
* Water, traversable only with a swimming ability
* Universal walls (above the sheet, fold-proof) and filter walls (block blocks, not the player) - built 2026-09-28, see §3  

Unlockable ideas, same status, same Checkpoint 1 deadline: swimming, push/pull (possibly granted early as a tutorial), free movement to the back of the sheet, rock breaking.

Collectables: optional, no mechanical effect, narrative flavour only. Same status.

**Structural implication, which does hold regardless of what gets picked:** build so that elements are *data-driven and additive* — an ability is a flag consulted by an element, not a code branch; an element is a component, not a subclass of a bespoke hierarchy. The list above will shrink and change, and the cost of that should be deleting prefabs, not refactoring systems.

One item worth calling out early because it constrains §5: **"floats up if covered"** means a covered object is not necessarily just hidden — some object types may need to relocate onto the flap. So the occlusion system should *notify* objects that they've been covered and let them respond, rather than blanket-disabling everything under the flap. That's cheap to build now and expensive to retrofit, even if the float-up element itself never ships.
