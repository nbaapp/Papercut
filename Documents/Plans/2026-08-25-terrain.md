## 5. Components & data

### `Ability` (new, enum)

```csharp
[Flags] public enum Ability { None = 0, Swim = 1 << 0 }
```

A new unlockable is a new member. `None` means "no ability".

### `PlayerAbilities` (new, on the Player prefab)

- Responsibility: the single source of truth for which abilities the player currently holds. Nothing else stores ability state.
- Serialized: `[SerializeField, Tooltip] Ability abilities = Ability.None;` — shown as an enum-flags mask. The tooltip states that the value saved on the prefab is the player's **starting** ability set, so a test toggle saved by accident is visible for what it is. **Editable in the Inspector during Play Mode** so Aaron can toggle Swim to test water: `OnValidate` only sets a dirty flag; `Update` raises `Changed` (physics calls are not made from `OnValidate`).
- Public surface:
  - `Ability Abilities` — the current set.
  - `event Action Changed`. Also raised from `OnEnable`, so regions re-apply their ignore-pairs if the player is ever toggled.
  - (`Has(Ability)` was planned and removed in code review: nothing used it — `TerrainRules` is the one consumer and takes the raw set.)
- No `Grant`/`Revoke`: nothing calls them yet (unlockable pickups are out of scope). A pickup adds a mutator when it exists.
- Not a tunable in the §4a sense (it's game state), but it is intentionally Inspector-editable.

### `TerrainRules` (new, static)

```csharp
public static bool IsPassable(Ability owned, Ability required)
    => required != Ability.None && (owned & required) == required;
```

Semantics: a region with `required == None` is a wall — nothing lets you through. Otherwise the player must hold **all** of the required bits. This is the whole rule; it lives in one pure function so it is testable and so "what counts as passable" has exactly one home.

### `TerrainRegion` (new, on Wall/Water prefabs)

- Responsibility: a free-placed, static region of the sheet that is either untraversable or traversable only with an ability. Owns a non-trigger `Collider2D`.
- `[RequireComponent(typeof(BoxCollider2D))]`, `[DisallowMultipleComponent]` — boxes are what Aaron asked for and what Unity can auto-add.
- Serialized:
  - `[SerializeField, Tooltip("Ability the player must hold to cross this region. None means it is a wall and can never be crossed.")] Ability requiredAbility = Ability.None;` — a design value per prefab, hence Inspector.
- Public surface:
  - `bool IsPassableBy(PlayerAbilities player)` (a `RequiredAbility` accessor was planned and dropped in code review — no caller) → `TerrainRules.IsPassable(player.Abilities, requiredAbility)`.
- No "kind" field. Wall and Water differ only by `requiredAbility` and tint.
- Gizmo: draws the box from `offset`/`size` under `Gizmos.matrix = localToWorld` (same pattern as `Exit`) — grey for walls, blue for gated regions — so the collision boxes are visible over the art in the Scene view (this is the "did I forget a box over that drawn rock" check).
- `Start`: warns (`LogWarning`) if this region's box overlaps any `Exit` box on the same sheet, because a region in an exit's arrival strip would spawn the arriving player inside a solid collider (see §6).

## 6. Behaviour

### Blocking and gating

The player is a dynamic `Rigidbody2D` with a `CircleCollider2D`; a region is a static non-trigger `BoxCollider2D`. With nothing else done, Physics2D blocks the player at every region — the **wall** case is free.

Gating uses `Physics2D.IgnoreCollision(regionCollider, playerCollider, ignore)` per region:

1. `TerrainRegion.OnEnable`: find the player's `PlayerAbilities` (`FindAnyObjectByType<PlayerAbilities>()`), cache it and its `Collider2D`, subscribe to `Changed`, and call `Apply()`.
2. `Apply()`: `Physics2D.IgnoreCollision(myCollider, playerCollider, IsPassableBy(player))`.
3. `PlayerAbilities.Changed` → `Apply()` on every enabled region.
4. `OnDisable`: unsubscribe. `OnEnable` re-applies on re-activation (e.g. the fold system turning `Back` on). **Untested in this task** — nothing activates `Back` yet; the fold task must verify it.

Why per-region `IgnoreCollision` rather than a physics layer per ability: it needs no layer bookkeeping, scales to any number of gated kinds, and keeps "who may cross what" in `TerrainRules` instead of the collision matrix. Cost is one lookup per region per enable and one call per region per ability change — tens of objects; negligible.

### Failure modes (no silent failures)

- Region not under a `Sheet` → `LogError` naming the object; still blocks (safe default).
- No `PlayerAbilities` in the scene at `OnEnable` → `LogError`; region stays blocking. (In the Desk scene the player is a scene object, so this only fires if the prefab lost its component.)
- Collider on the region is a trigger → `LogError` "must not be a trigger; fixing at runtime, please fix the asset" and set `isTrigger = false` (mirrors `Exit`'s inverse check).
- `requiredAbility` is a combination of bits → fine; the player needs all of them. Documented in the tooltip.
- Player is *inside* a gated region when the ability is revoked (Inspector toggle during Play Mode): Physics2D resolves the overlap by pushing the player out on the next step. Accepted; it is a testing-only situation, and is in the manual test list.
- **Arrival strips must stay clear.** `ScreenNavigator.EntryPosition` places an arriving player `entryInset` inside the edge they came through, at the along-edge coordinate they left at. A region there would spawn the player inside a solid box and Physics2D would depenetrate in an arbitrary direction. Authoring rule: do not place terrain over an `Exit` box. Enforced softly by the `Start` overlap warning above.

### Ground

Ground is the absence of a region. No component, no collider, no "ground" prefab. Recorded here so nobody adds one.

### Placeholder visuals

Each prefab has a `SpriteRenderer` on the region object itself (not a child) using `Placeholder Square.png` in **Tiled** draw mode, with `BoxCollider2D.autoTiling = true` so resizing the sprite with the Rect tool resizes the collider to match. Tint: wall `(0.35, 0.35, 0.35, 0.9)`, water `(0.35, 0.6, 0.9, 0.7)`. Material: URP `Sprite-Unlit-Default`. Local z = −0.05 so the sprite draws in front of the face `Surface` quad (camera looks along +z). These are placeholders — once the Photoshop art carries the drawing, Aaron disables the `SpriteRenderer` on the prefab and the boxes become invisible collision. The tints are set on the prefab, not in code.

### Authoring workflow (what Aaron does)

Open a sheet variant → drag `Wall` or `Water` under `Front` (or `Back`) → move/resize with the Rect tool, keeping clear of the Exit boxes. That is all. A new gated kind = duplicate `Water.prefab`, change `requiredAbility`, change tint.

## 7. Interfaces & seams

- **`TerrainRules` is the seam between "what makes terrain passable" and "how Physics2D is told".** The fold/occlusion system never needs to know about Physics2D ignore-pairs; if the layering rule in Bible §5 ever changes how crossing works, `TerrainRules` is the one place.
- **`PlayerAbilities.Changed` is the seam for unlockables.** A pickup calls `Grant(Ability.Swim)`; nothing else changes.
- **Occlusion is deliberately not seamed here.** When the occlusion task defines its "you have been covered" notification, `TerrainRegion` implements it — a terrain region is then just another coverable object, same path as blocks.
- **Cutting the feature:** delete `Prefabs/Terrain/` and `Scripts/Terrain/`. Nothing in `Sheet`, `Desk`, `PlayerMover`, or the navigator references terrain. Cutting *water only* = delete `Water.prefab` (and, optionally, the `Swim` enum member and `PlayerAbilities`).

## 9. Assumptions (engineering)

1. `Physics2D.IgnoreCollision` is the gating mechanism (rationale in §6). Alternative — a layer per ability + `Physics2D.IgnoreLayerCollision` — is one line but adds a layer per kind; rejected for scaling reasons, not correctness.
2. `PlayerAbilities` is looked up with `FindAnyObjectByType` in `OnEnable`. There is exactly one player; a registry would be pre-generalization.
3. Regions are static: they don't move, so `IgnoreCollision` pairs are set once per enable/ability change, never per frame.
4. The placeholder sprite/tints are dev visuals. They are on the prefab so removing them is an Inspector click, not a code change. Art is out of scope.
5. `requiredAbility` semantics = "all bits". An "any of" mode would be a second field; not building it until a kind needs it.
6. Regions live at sheet-local z = −0.05. The face `Surface` quads are at 0 (Front) and 0.01 (Back); the camera is at z = −10 looking +z, so nearer = more negative. The exact value is an implementation constant, not a tunable.
7. No changes to `PlayerMover` — collision is entirely Physics2D as its doc comment already states.
8. Hand-authored YAML for prefabs; nested prefab instances inside variants follow the derived-fileID rule and are verified by `check_links.py`. Script `.meta` files carry fixed GUIDs so the prefabs can reference them before the editor imports anything.
9. **"Conditionally traversable" = gated on a player ability.** Aaron's sentence could also cover terrain gated on world state (a switch, a fold). Narrowest-open reading: `TerrainRegion` consults `PlayerAbilities` only; a world-state-gated region would be a separate component that consults a different flag, not a condition-source abstraction built now. Flagged in the report.
10. **Partial coverage by a flap is deferred to the occlusion task.** Choosing boxes means a region half under a flap must either be clipped at runtime (box → polygon) or handled by a per-region coverage rule; that is the cost Bible §3 warned about, it interacts with Bible §5 `[DECIDE]`, and it is recorded in the Bible note rather than decided here.
